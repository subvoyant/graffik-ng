# Graffik NG — Knowledge Hub

**Purpose:** read this file first; then read only the digest(s) for what you're touching. This replaces re-reading source for orientation. Trust digests for the map; verify against source before changing a detail. Update digests in the same change that alters behavior (ADR-0000).

**Project:** modern TypeScript/Electron software driving the Dynamic Perception NMX 3-axis motion controller for repeatable multi-pass camera moves ("multiplicity") — a maintained successor to the abandoned Graffik apps. MIT, fresh-from-spec (ADR-0003). First milestone: jog → record → replay identical passes.

## Load-bearing invariants (memorize these)

1. Packet = `00x5 FF` header · address (default **3**; broadcast **1**) · sub-address (0 gen / 1–3 motors / 4 camera / 5 key-frame) · command · length · **big-endian** payload.
2. USB serial is **19200 baud** — firmware `USBSerial.begin(19200)`; must be set explicitly.
3. Queries are commands **≥100**; sets/actions ack `0x01/0x00`. Query "floats" are **fixed-point ×100 longs** — divide by 100.
4. **One command in flight**; responses match FIFO. Never await a broadcast (nodes never reply). Jog-speed (motor cmd 13) gets **no reply** while joystick/Graffik mode is on.
5. Command numbers come **only** from the 2018 firmware dispatch (ADR-0004) — older refs disagree (prog-mode 22 not 0x22; motor 10 = end-limit-here; motor send-to-start 23 not 25).
6. `handshake()` = query firmware version (expect **v70**) + Graffik mode on. Arm the **joystick watchdog** (gen cmd 14) before any jogging.
7. E-stop = broadcast stop (cmd 2) + KF-stop (cmd 8); `NmxClient.stopAll()` flushes the queue first and jumps the line.
7b. **Stopping is instant and always available; starting requires deliberation** (ADR-0021). The physical STOP button fires on press with no hold and no confirmation; every action that can move the rig is a 600 ms hold. The button loop runs whenever a controller is present — never tied to the jog toggle, because a programmed pass is when you need it most. A vanished controller mid-jog zeroes every axis.
8. KF uploads end each axis with `endTransmission` (KF cmd 16) or the program silently isn't finalized.
9. No GPL code may be pasted/ported in (ADR-0003) — reference repos are for *facts* only.
10. Renderer never touches serial/Node; hardware ops only via the IPC surface (ADR-0007).
11. Motion math has ONE owner: core `computeVelocities`/`splineAt` feed both the editor preview and the firmware upload (ADR-0009). Never duplicate it in the UI.
12. Programmed moves are firmware-gated (v70) with explicit override only; jog speed hard-clamped ±4000 steps/s; cue countdown is host-side for both engines.
13. Soft limits are enforced in the MAIN process (jog request + 90ms monitor + pre-upload validation), never the renderer (ADR-0013). Motion away from a violated bound must always stay allowed.
13c. **A taught limit is a STEP COUNT, and a step count is only a place if the controller's origin holds** (ADR-0030). `ee_load_curPos` defaults to **false**, so an NMX forgets its position across a power cycle unless told otherwise — and then stored limits describe somewhere else on the rail while the operator still believes in them, which is worse than no limits. General **119** (power-cycled since last asked) is a **one-shot latch consumed by the first reader**: ask once per connection, keep the answer, and never read `false` as an all-clear. General **131** says whether position is restored. Power-cycled + no restore ⇒ the taught bounds are **not enforced** (they read as untaught, which re-arms 13b's creep cap) and programmed uploads are refused; teaching a bound, or the operator saying so on a button, clears it. The app never writes the controller's EEPROM (cmd 30) except on an explicit button.
13b. An axis with **neither bound taught creeps at 500 steps/s** (ADR-0023). The first jog necessarily precedes any limits — they are taught by jogging to them — so this is the one moment 13 cannot help. Self-clears on the first taught bound; no override switch, because an override is a thing you leave on.
14. **Frames are the authoring unit; milliseconds exist only at the protocol boundary** (ADR-0014). Rates are exact rationals — 23.976 is 24000/1001, never the decimal. Drop-frame is legal only at 29.97/59.94. Conversion happens in `filmDurationMs`/`filmCueMs`/`filmAxesToMs` and nowhere else.
15. 3D export samples the SAME solver as the upload, once per frame, and states its own `metersPerUnit`/`upAxis` (ADR-0015). Steps→mm/deg needs a calibration MEASURED on the rig; without it an export is a shape, not a camera move. **Export 3D… → Measure… is how it gets measured** (ADR-0020) — spans, not absolute positions; the spread between spans IS the error bar.
16. Anything that must be identical between passes cannot be timed by the host (ADR-0016, and ADR-0005 again). Host-scheduled cues are ±20 ms and non-repeatable; frame-exact cues must be uploaded to a device and triggered once.
17. UI uses design tokens only — **no literal hex in new UI** (ADR-0012). Axis colors are validated for colorblind separation; a new series color comes from the next validated categorical slot, never invented. When the validator fails all-pairs, **facet** into labelled groups that reuse passing slots — never widen the palette past what passed.
18. A lens position is a **fraction of barrel travel, 0..1** — never a distance (ADR-0017). Real units come from witness marks (`LensMap`); with no map the UI shows percent and the 3D export omits the axis rather than inventing one. Lens keys use the same solver as motion (ADR-0009) and retime with the move (ADR-0014).
19. Lens curves are **uploaded and run device-side** on GRAFFIK-TRIG **protocol v2** (ADR-0018) — same board, same `GO` as the cues. The host sends **samples, not keys** (no second solver — ADR-0009), decimated under a stated vertical error bound; **the firmware may only interpolate linearly**, because that is what the bound is stated against.
20. **An un-homed lens axis refuses to run.** A stepper is open loop; `LCAL` against both mechanical stops is the only thing that makes a position mean anything, and the board — not the host — is the only party that knows whether it has homed since power-up. A remembered travel figure is a pre-flight hint, never a claim.
21. **`ABORT` stops lens motion and HOLDS.** Never homes, never releases, drivers stay enabled. A free-wheeling focus ring under a heavy lens is how you lose the lens.
22. **Marks belong to a LENS, not to a move** (ADR-0019). The library is merged by **id**, never by name; import never replaces; forgetting a lens never unmarks a move already using it.
23. **The simulated device must be exactly as strict as the firmware.** A simulator more permissive than the board means every test passes and the rig fails; `firmware/graffik-trig/test/parity.mjs` enforces it in CI and has already caught one divergence.
24. **A headless runner refuses work it can only partly do; a supervised UI says so and proceeds** (ADR-0026). A `.graffik` carries three independently-executed subsystems (NMX motion, cues, lens) and nothing guarantees the machine you are on can reach all three. `nmx run` exits **1** naming what it cannot execute unless given `--motion-only`; the app logs `N lens lane(s) NOT driven — pull by hand` at arm time and runs, because a person is looking at it and hand-pulling is a legitimate workflow. The line is whether a human is in the loop at the moment of the decision — not GUI vs terminal. **The CLI enforces no soft limits at all** (ADR-0013 lives in the Electron main process), including on the pre-pass `sendToPosition`; it now says so on every run.
25. **What the rig DID is recorded, and compared at matched percent** (ADR-0027). Sampling during a pass is safe because the firmware steps off **Timer1**, not the main loop — a query costs loop time, not steps. **Motor query 106 is rescaled to `(lastMs/ms) × pos` while a motor is mid *send-to*** (a send silently forces quarter-stepping); **query 124** answers "am I sending?", and any sample where it is true is set aside rather than averaged in. A key-frame move never sets that flag; the pre-pass goto does. The join key between passes is the **controller's percent**, never host time. Progress is reported in whole percent, so a matched-percent comparison has a **resolution floor** — a result at or under it is worded as a bound, not a measurement, and `deviationLines` is the single owner of that wording. Sampling **never aborts the take**: a failed read is a `null`, and every stop path CLOSES the recording rather than discarding it.
26. **Plan type is `CONT_VID` (2), and it decides what percent complete is divided by** (ADR-0028). `Motion_Engine.ino` defines three plan types — SMS 0, CONT_TL 1, CONT_VID 2 — and `kf_getPercentDone()` divides by move time **only** on CONT_VID; on anything else it divides by move time **plus the camera's focus and trigger time**. Since percent anchors the playhead (ADR-0025) and joins recorded passes (ADR-0027), the wrong plan type silently skews both. **Both engines set it explicitly on every arm/upload and READ IT BACK on general query 118** — the failure guarded against is not a dropped write, it is something else having set it. CONT_VID also makes the classic engine fire the shutter once at program stop (start/stop record).
27. **The command vocabulary is checked against the firmware dispatch, in CI** (ADR-0029). `reference/nmx-dispatch.json` holds every `case N:` each handler reaches plus the firmware's own comment — facts, not code — so `scripts/audit-vocabulary.mjs --strict` can verify every builder targets a command that handler actually has, **without CI needing the GPL clone**. ADR-0004 stopped being a rule people follow and became one CI enforces. Coverage is **reported, never failed on**: a vocabulary describes a device and completeness is a feature. It is deliberately separate from the dead-export audit, which could never find this class — `general` being reachable makes every member of it reachable.
28. **Ask the controller whether the move is physically possible, before running it** (ADR-0031). Key-frame **105**/**106** validate velocity and acceleration for the *selected* axis; classic **general 129** validates the whole program and **motor 120** names the axis. A move that exceeds what a motor can deliver **does not fail loudly — it fails to track**, which on a shoot reads as a belt problem for an afternoon. One pre-flight per pass asks the device first, then arms cues and lens lanes; it sits outside the cue check because that returns early when nothing is attached, and a plain three-axis move is exactly where this still matters. **Not being able to ask is not being told no**: an unanswered query reads as *unchecked* and never blocks, because a check that blocks on a timeout is a check that gets routed around.
29. **A recording is written to disk the moment the pass ends** (ADR-0032) — `userData/recordings/`, **disk before the in-memory list**, because the list has a cap that drops the oldest and saving after it could discard a pass before writing it. Previous sessions load through `parsePassTrace`, which skips and **counts** one unreadable file rather than losing the rest. Nothing is deleted; the load limit bounds what is read. A failed write is said out loud with the remedy.

Three causes, none of them the drawing: `setInterval` instead of `requestAnimationFrame`; `Math.round` pinning the playhead to whole frames; and the 500 ms re-anchor being a **snap**. Now the reading moves a *target* and the drawn position converges **by adjusting speed, never by assigning position** — monotonic, so it cannot step backwards. The first attempt at that fix clamped with `Math.min(predicted, …)` and *did* step backwards; **measurement caught it, reading the code had not.** Measured: 60 fps, `render()` 0.74 ms on a six-lane 30 s move, 0 backwards steps, 0 spikes.
- **Done (v0.26):** **recordings survive the session** (ADR-0032). The flight recorder held everything in memory for five versions and the documented mitigation was "export the CSVs" — which is not a mitigation on a shoot. The first hardware day is both the day the measurements matter most and the day the app is most likely to be restarted. Each pass is now written to `userData/recordings/` the instant it ends, **before** the capped in-memory list can drop it, and read back at startup through a validating parser so one bad file cannot cost you the rest. The bring-up report names the folder, the file count, and anything it could not read. 404 tests.
- **Done (v0.25):** **the controller has always been able to say whether a move is possible, and we never asked** (ADR-0031) — the last big item from v0.23's coverage report. Key-frame queries 105/106 were **in the vocabulary, called by nothing**, for twenty-four versions. A move beyond a motor's reach does not fail loudly, it fails to track. Now one pre-flight per pass asks the device first. Building it found two more: the **simulator answered a bare ack** to 105/106 and to key-frame 121 (so the flight recorder's device timing had been reading as "incomplete" since v0.23), and the first model of it checked **knot velocities** — passing 5000 steps/s on a 1000 steps/s rig, because a two-point move has zero velocity at both keys and all its speed in between. And `computeVelocities` accepted points with no usable time — `undefined <= undefined` is false, so the strictly-increasing guard passed and every abscissa reached the wire as NaN. It refuses now. 398 tests.
- **Done (v0.24):** **taught limits can go stale, and now they say so** (ADR-0030) — straight out of v0.23's coverage report. A taught limit is a *step count*, and the firmware's `ee_load_curPos` defaults to **false**, so an NMX forgets its position across a power cycle: the stored numbers then describe different places on the rail while the operator still believes in them. General 119 tells us it power-cycled, general 131 whether it restores position — and 119 is a **one-shot latch consumed by whoever reads it first**, so the app asks exactly once per connection and never reads a `false` as an all-clear. Voided limits are **not deleted** — they stop being *acted* on, which re-arms the creep cap, and uploads are refused until a bound is re-taught or the operator says so on a button. The app offers to turn on position restore rather than writing somebody's EEPROM on connect. 390 tests.
- **Done (v0.23):** **the vocabulary is now checked against the dispatch** (ADR-0029). v0.22 was found by chasing one value to the firmware; there are 119 command builders and chasing them by hand is work that goes stale. The dispatch is extracted into a committed fact table and `check.sh` verifies every builder against it. **First run found `general.setMaxStepRate` — general cmd 11, deprecated in firmware 0.70, the exact version we gate on.** `serMain` has no case 11 and the default branch does not reply, so a caller would have stalled the one-in-flight queue until timeout. Nothing called it; removed. Two coverage gaps closed on purpose: key-frame query **122** *is* the denominator the firmware divides percent by, so every recorded pass now reads the device's own arithmetic and `timingCheck` compares it against the duration we uploaded — catching ADR-0028's bug class **from the rig**, not just from a mode read-back. 378 tests.
- **Done (v0.22 — found by checking an assumption in v0.21, one hour old):** **the plan type was wrong, and it decides what percent means** (ADR-0028). Before trusting the recorder's percent→frame mapping I went to the dispatch to confirm percent is time-based. It is — but `kf_getPercentDone()` divides by move time **only** on `CONT_VID`, and on anything else by move time **plus the camera's focus and trigger time**. The vocabulary described cmd 22 as "0 = SMS, 1 = continuous" and typed it `0 | 1`, making `CONT_VID` unrepresentable; the classic path sent CONT_TL and **the key-frame path never set a plan type at all**, so a KF pass ran under whatever was last latched. With a 2 s exposure that is a 17% skew on the playhead and on every recorded comparison, with entirely plausible-looking numbers. Now `PLAN_TYPE` has all three values, both engines set `contVideo`, and it is **read back on query 118** and named in the bring-up report — or reported as "not read back" when nothing checked. 364 tests.
- **Done (v0.21):** **The flight recorder** (ADR-0027) — twenty versions in, everything this software knew was about the move it *sent*; nothing had ever known what came back. Every pass is now recorded while it runs, on the poll that was already there for the progress bar, and passes are compared **at matched controller percent** rather than host time. Three firmware facts made it possible and one of them would have produced a beautiful wrong dataset: query 106 is silently rescaled during a *send-to* because a send forces quarter-stepping, and query 124 is how you find out. The **resolution floor is computed and stated** — whole-percent progress cannot resolve motion finer than one percent of the path, so a good result is reported as a *bound*, not a measurement, because that number will be quoted later. Recorded passes overlay the lanes in the axis's own hue (dashed — identity is the series, provenance is style) and are **included in the lane's y-scale**, because a deviation big enough to leave the lane is the whole point. The bring-up report carries per-pass coverage and an automatic last-two-passes comparison — the number that ratifies or refutes ADR-0006. This does **not** replace the five-pass tape check: that measures the endpoint better, this measures everything in between. 361 tests.
- **Done (v0.20 — found while packaging v0.19, not by a test):** the **CLI was silently dropping whole subsystems**. `nmx run` loaded a file with lens axes, ignored them, ran the motion axes and **exited 0** — a lie to whatever script read that code. It now refuses, naming each one, unless given `--motion-only` (ADR-0026), and discloses that it enforces no soft limits at all. `check.sh` gained the first end-to-end exercise of the CLI run path (refusal + a full simulated pass); its only previous check was `nmx info --sim`. Pulling the same thread found the jog-slice digest's *Known gaps* paragraph frozen at ~v0.9, still claiming there was **no lens motor driver, no lens library and no gamepad button bindings** — all three shipped in v0.11/v0.12/v0.14. **Negative prose is what rots**: you revisit a doc when you add a feature, never when you close a gap.

## Maintenance rules (the operating model — short version)

- Behavior/API/invariant changed → update the module digest + this hub's map/state **in the same commit**; refresh the "Verified against" stamp.
- New load-bearing decision → new ADR (next number), add to `docs/adr/README.md` index; never edit Accepted ADRs — supersede.
- Keep digests token-lean: facts, invariants, gotchas, pointers — no code dumps, no secrets, no narratives.
- Session end: update "Current state & next steps" here and the project decision log.
