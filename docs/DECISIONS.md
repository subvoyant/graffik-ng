was learned. ADRs in `docs/adr/` are the canonical *why* for load-bearing
decisions; this file is the log around them, including the process lessons an

## 2026-08-15 (post-Phase 0 recon — see claude/phase0-codebase-reality-report.md)
- **Base repo decision REVERSED:** do NOT fork Graffik_Legacy (Qt 4.8.1, protocol incompatible with NMX — no sub-address support). Legacy is UX/feature reference only. The reboot repo (DynamicPerception/Graffik) contains the real NMX protocol implementation (~1,100 lines) — reference implementation.
- **Platform: TypeScript + Electron.** Strictly separated headless `nmx-protocol` core package; Electron shell for UI. Rationale: firmware executes moves (determinism on-device), UI is 80% of remaining work and web tech is fastest for timeline/keyframe editors, electron-builder solves macOS notarization, Windows nearly free.
- **Protocol implemented fresh from spec** (official PDFs recovered from nanoMoCo_Firmware repo + Sample Commands.txt + firmware source as ground truth), NOT ported from GPL code → new codebase's license is our choice (MIT chosen).
- Key protocol facts: packet = `00 00 00 00 00 FF` + address (default 3) + subaddr (0 gen / 1–3 motors / 4 camera / 5 key-frame engine) + command + length + big-endian payload. USB serial **19200 baud**. Queries are commands ≥100. Broadcast start/stop/pause = e-stop primitive. Firmware has native key-frame engine (what NMX Motion app uses for real-time moves).
- Reference repos: DynamicPerception/{Graffik, Graffik_Legacy, nanoMoCo_Firmware, NMXComs, NMXCommander, nmx-motion-ios}. Forks (djordan2, thisdroneeatspeople) contain nothing unmerged — dropped.

## 2026-08-17 (repo hygiene, CI, delivery lessons)
- Repo pushed to **github.com/subvoyant/graffik-ng**. `.claude/` memory scratch is gitignored; the knowledge system (`docs/adr`, `docs/digests`, `CLAUDE.md`) is deliberately **in** the repo — it is project documentation, not agent scratch.
- **Lockfiles must be committed** (ADR-0011); CI installs with `npm ci`. Failure mode hit once: a devDependency added to `package.json` without re-running `npm install` → `npm ci` fails "Missing <pkg> from lock file". **My error, not the owner's** — recorded so the reflex is to check the lock, not to apologize.
- The **CI badge is authoritative**; do not report a run green from a page summary that cannot be verified. (Bitten again 2026-08-17: a `?query=is%3Acompleted` URL hides an in-progress run, so the top row was the *previous* commit. Check the commit title matches the SHA you pushed.)
- Commit identity: commits were authored under the Cowork address; the owner added `software@` to their GitHub account so the repo shows under their contributions.
- **Delivery lesson (repeat):** deliver via the device bridge, never the chat-download dance. The mounted FS refuses `tar` overwrite → extract to `/tmp`, then `cp`. It also refuses to overwrite one large binary (`icon.icns`, 2.3 MB) — skip unchanged binaries when copying.
- **Never run `git status` through the device bridge.** It takes `.git/index.lock` and the bridge cannot unlink it, leaving a stale lock that blocks the owner's next git command. Use `git --no-optional-locks status`, or read `.git/refs/**` directly.

## 2026-08-17 (v0.6 — safety, persistence, controller feel)
- **ADR-0013: soft travel limits, enforced host-side.** The NMX has no encoder feedback, so limits must be *taught by jogging*. Enforced in the **main process** at three points (jog request w/ 250 ms lookahead · 90 ms jog monitor · pre-upload film validation) so no renderer bug can bypass them. Motion *away* from a violated bound is always allowed — a rig parked outside its limits must stay recoverable. Firmware-side limits (motor cmds 9/10/33) rejected as the primary mechanism: unvalidatable without hardware, and they mutate persistent controller state other apps see. Revisit after bring-up.
- **Preferences persistence** (`userData/preferences.json`): window bounds, last port, jog speed, limits, gamepad config, recent files. `lastPort` is **remembered but never auto-connected** — opening a serial port stays an explicit human act.
- **Gamepad bindings + ballistics** (owner request): per-axis mapping with a "bind…" learn mode that captures whichever stick moves (controller axis numbering is not standardized, so never make the user know indices), invert per axis, deadzone / response-curve exponent / max-speed scaling, live response-curve plot. Ballistics **renormalizes after the deadzone** — a naive `raw^curve` leaves a speed discontinuity at the threshold, which on a slider is a visible jerk in the shot.
- **Headless-render verification became part of the loop.** Rendering `index.html` in Chromium (via the v0.5 preview stub) and *looking at the picture* caught three defects code review missed: (1) taught limits were **invisible** on the timeline whenever they sat >15% outside the move, because auto-scale ignored them — the reassurance failed exactly when it mattered; (2) the rail overflowed and scrolled as soon as a keyframe was selected; (3) the last ruler label rendered clipped. **Keep this step: build it, render it, look at it.**
- Same render produced the **fresh README screenshot** — no need to ask the owner for a grab.
- **The rail's vertical budget is now spent.** Worst case fits with 0 px to spare at the default 820 px window. The next piece of always-visible configuration goes in a **modal**, not a rail panel.
- 57 core tests green.

## 2026-08-17 (v0.7 — timecode, 3D export, event schema)
- **ADR-0014: frames are the authoring unit; milliseconds exist only at the protocol boundary.** Milliseconds had propagated outward from the firmware until they reached the operator, who does not think in them. `.graffik` **v2** stores `timebase` + `durationFrames` + `cueFrames` + `startFrame` + per-keyframe `frame`; conversion happens in `filmDurationMs`/`filmCueMs`/`filmAxesToMs` and nowhere else.
  - **Rates are exact rationals** — 23.976 = 24000/1001, never the decimal. The rounded decimal drifts ~3.6 ms per 1000 frames; between two passes of a composite that is visible misregistration.
  - **Drop-frame is legal only at 29.97/59.94** and is refused elsewhere: at 23.976 the correction is 14.4 frames per 10 min, not a whole number, which is why no DF standard exists for it. Typing a DF-skipped timecode (`00:01:00;00`) is rejected, not rounded — those timecodes do not exist and accepting one hides a typo.
  - Changing the timebase **retimes** the move (same real seconds, new frame count). Keeping frame numbers would silently change a move already matched to a performance.
  - Timecode is bridged **synchronously** into the renderer by preload (`window.tc`) so there is exactly one implementation; the app now hard-depends on the core being *built*, and preload fails loudly if it is not.
  - v1 files migrate at an **assumed 24 fps**, with the assumption written into the file's `notes` rather than hidden.
- **ADR-0015: 3D export via OpenUSD + `.chan`, not Alembic.** USD is the only common format that *states its own scale* (`metersPerUnit`, `upAxis`) — every other option makes the importer guess. Alembic's Ogawa container has no maintained pure-JS writer, so writing it means a native dependency in a dependency-free core.
  - **Scale = a measured `RigCalibration`** (steps/mm, steps/deg ×2, nodal offset, head height). The NMX has no encoder, so nothing in software can derive it. Procedure added as `docs/HARDWARE-BRINGUP.md` Phase 6. Two diagnostics: a ×100 error is the unit setting; ×2/4/8/16 is microstepping.
  - Export writes the **mechanism** (Carriage→Pan→Tilt→Camera), not a flattened matrix, and samples the *same* solver as the upload, once per frame.
  - `nodalOffsetMm` is not optional in practice — a head swings the camera on an arc, and ignoring it is why tracked CG slides against a plate on tilts.
- **ADR-0016: timeline events, and where they are scheduled.** ADR-0005 applied again: *anything that must be identical between passes cannot be timed by the host.* Tier 1 (host) ≈ ±20 ms and non-repeatable — fine for cue lights. Tier 2 (cue list uploaded to a microcontroller, one `GO`) is required for focus pulls and animatronics. The UI must show which tier a cue is on.
  - Backend survey: Arduino-class serial, **Enttec DMX USB Pro** and OSC all need **no new dependency**; MIDI is the outlier (every Node binding is native, and Web MIDI would breach ADR-0007). Device protocol is versioned plain text so it can be implemented on any board and read in a serial monitor at 2 a.m.
  - **Safety gap recorded:** an armed cue list is state `stopAll()` does not reach. `ABORT` must be wired into the e-stop before any Tier-2 output drives something that moves.

## 2026-08-17 (v0.8 — the cue system, ADR-0016 implemented)
- **`trigger.ts` in the core.** `TriggerBackend` seam (`describe/outputs/supports/fire/arm/start/abort/close`) with a declared `tier`, mirroring the `PortLike` seam. Three implementations: `SimulatedTriggerBackend` (records what would have fired), `SerialTriggerBackend` (GRAFFIK-TRIG v1 over any `PortLike`), and `SimulatedTriggerDevice` — the **device** side, with its own `tick()` clock — so Tier-2 timing is tested end to end without a board. Same discipline as `SimulatedNmx`.
- **`CueScheduler` takes injected time** (`advanceTo(elapsedMs)`): deterministic under test, timer-driven in the app. Two deliberate behaviours: it **fires a late cue rather than dropping it** (a missed cue light is invisible; a late one is explicable), and it exposes `worstJitterMs()` so the Tier-1 caveat is a *measured number* rather than a claim in a document.
- **Unroutable cues abort the pass before it starts.** Discovering an unbound target from a log afterwards is the expensive version of the same information.
- **The serial backend refuses an unknown protocol version** rather than guessing a command set — ADR-0004's trap, applied to a second device. It also refuses a partial `ARM` (better no cues than some), and `abort()` is fire-and-forget so the e-stop path cannot hang on the device that may be what failed.
- **Reference firmware shipped:** `firmware/graffik-trig/graffik-trig.ino`. Non-blocking pulses — a `delay()` inside a cue would make every later cue late, which is the exact failure the board exists to prevent. GPI edges reported with the device's own timestamp.
- **Safety gap CLOSED:** `stopAll()` now aborts every backend **first and independently of the NMX**. If the link to the controller is what has failed, the cue about to fire is still ours to stop.
- **UI:** cue lane above the axes (cues belong to the move, not to an axis), frame-snapped, sustained cues drawn as bars. The rail inspector became **context-sensitive** (`selection = {kind:"key"|"cue"}`) — one panel serves both, which is the 3D-app idiom and the only thing the height budget allowed. ⚡ Cues… modal holds the device and the target bindings, with the tier explanation *in the dialog*, not only in the ADR.
- **Process note:** I wrote a test named "refuses an unknown protocol version" that asserted nothing meaningful — dead code and a vacuous expectation. Caught it on review and made it real by giving the simulated device a settable version. **A test that claims coverage it does not have is worse than no test**, because it removes the pressure to write the real one.
- 159 tests. Pushed as `d89ea69`.

## 2026-08-17 (v0.9 — DMX + OSC backends, measured jitter)
- **Both new backends cost zero dependencies**, which is why they were chosen ahead of MIDI. The Enttec DMX USB Pro is an FTDI virtual COM port, so it rides the existing `serialport` package and the same `PortLike` seam; OSC is `node:dgram` with the encoder written here.
- **DMX framing gotcha, now an invariant:** `0x7E | label | lenLSB | lenMSB | data | 0xE7` — the **length field is LITTLE-endian**, the only such field in this codebase. The NMX is big-endian throughout. Two byte-order conventions living in one repo is exactly how a subtle framing bug is born, so it is called out in the source and the digest. Label 6's data starts with the DMX **start code**, so `dmxPayload` puts channel N at `payload[N]`; the widget rejects universes shorter than 24 channels, so short ones are **padded, never truncated**. Per Enttec's own API the host baud rate is a dummy value — the widget owns DMX timing.
- **DMX is state, not events.** A channel holds until changed. Two consequences that fall straight out: a `pulse` must **schedule its own release** (nothing else will), and `abort()` **blacks out** — a cue system that leaves a lamp at full after an e-stop has not stopped.
- **OSC padding is the classic bug, so it is a named tested function.** An OSC-string is null-terminated *and then* padded to a multiple of 4, **always with at least one null** — `"data"` occupies 8 bytes, and the type-tag string pads by the same rule. Numbers big-endian. JS numbers are ambiguous, so the rule is stated: integers → `i`, everything else → `f`, with `{int:…}`/`{float:…}` to force it, because some receivers silently ignore the wrong type. UDP confirms nothing, and the dialog says so.
- **Real bug caught by writing the tests: I had given `DmxTriggerBackend` two clocks** — a private counter advanced by `tick()` *alongside* injected timers. The test caught them disagreeing, but the production consequence was worse: nothing in the app ever calls `tick()`, so the rate limiter would have believed no time had passed and deferred every frame after the first. It would have "worked" while being wrong. Fixed to **one injected clock** (`nowFn` + `setTimeoutFn` from the same source), with the reasoning left in the source. **Rule: if you add timing to a class, inject it — never grow a second clock.**
- The other failure was mine in the test, not the code: I forgot the OSC **type-tag string pads by the same rule as any other OSC-string**, so `,isf` is 8 bytes, not 4.
- **Jitter is now observed, not asserted.** Every completed pass logs `N cues fired · worst lateness M ms (host-timed)` and names any cue more than 40 ms late. The Tier-1 caveat had been a claim in a document for three slices.
- Trigger transports (board, DMX, OSC) all close on quit, **aborting first** — a board holding an armed list, or a lamp left at full, is not "quit".
- 190 tests. Pushed as `9bb11d1`; CI #10 green in 1m 23s (commit title checked against the pushed SHA, per the earlier lesson).

## 2026-08-18 (v0.10 — lens axes: focus, iris, zoom · ADR-0017)
Owner's framing: *"Camera motion control without focus is less than ideal."* Correct, and sharper than it sounds — the rig repeats its path exactly and a human focus puller cannot, so the one place multiplicity breaks is the lens, and it breaks in the way composite work makes obvious.

- **`.graffik` v3 adds `lensAxes` as a collection SEPARATE from the motor axes.** Tempting to make focus "axis 4"; wrong. `FilmAxis.position` means NMX motor steps, uploaded to a three-axis key-frame engine, bounded by taught soft limits, converted by a rig calibration — none of that applies to a lens. The NMX also has exactly three motor channels and all three are spoken for. And the failure modes differ: a motion axis past its bound crashes a camera into a rail end; a lens axis past its bound stalls against a hard stop, which is *how it calibrates itself*.
- **The version was bumped even though the change is purely additive** — so a v0.9 build refuses a v3 file rather than opening it with the focus pull silently missing. A move file that quietly loses a pull is worse than one that will not open.
- **A lens position is a fraction of barrel travel, 0..1 — never a distance.** Real units come from a **lens map**: witness marks pairing a travel fraction with what the barrel reads there. Confirmed against the industry reference: the Preston FI+Z MDR "uses a lens calibration sequence to determine the mechanical limits of the zoom, focus, and iris rings," re-run whenever a motor is connected — that establishes the span — and then Lens Mapping records motor position at six discrete distances plus infinity, stored per lens in a 150-lens on-board library. Our `LensMark[]` is that list. Storing feet directly would bake one piece of glass into the move file and lie the moment anybody changes lenses.
- Falling out of that, and implemented as such: **no map still repeats exactly** and displays percent, never a fabricated distance; interpolation is linear **between adjacent marks** and **clamps outside** them (a focus scale is grossly non-linear, so a global fit is wrong everywhere and extrapolation is inventing data); iris maps often **descend**, so the inverse handles that; end-of-travel labels prefer the **engraving** (`∞`) over the map's number (`60.0m`), which claims a precision the barrel never had.
- **Same solver as everything else** (ADR-0009), clamped to 0..1. Lens keys retime with duration and timebase changes — a pull is timed to the move, not the wall clock.
- **Owner supplied the hardware direction mid-slice: Arduino-class board + stepper driver boards.** ADR-0017 §4 turns that into a spec rather than leaving it open. Lens curves are **uploaded before the pass and executed device-side**, started by the same single `GO` as the cue list — ADR-0005/0016 for the third time, and focus is *more* jitter-sensitive than a cue light. GRAFFIK-TRIG **protocol v2**: `LAXIS` / `LCAL` / `LKEY` / `LSEEK`. Design notes carried into it: the host uploads **samples, not keys** (the spline stays in the tested core — no second solver); **calibrate to the mechanical stops on connect** because steppers are open-loop and the stops are the only reference a barrel offers; **TMC2209** specifically, for StallGuard4 (finds the stop without a switch) and StealthChop (quiet enough to sit next to a microphone) — an A4988 is audible on a set and cannot detect a stall; **0.8 module** pinion, the cine gear standard; and **`ABORT` stops but HOLDS position** — never homes, never releases, because a focus ring that free-wheels on e-stop is a way to lose a lens.
- **Palette: a six-slot categorical set FAILED all-pairs CVD validation** (magenta↔aqua ΔE 1.6 deutan; yellow↔orange ΔE 10.6 *normal vision*). Per ADR-0012 the answer to "I need more series colours" is **faceting, not a wider palette**: focus/iris/zoom reuse validated slots 1–3 inside their own labelled band. Identity comes from the band and the direct label, never colour alone.
- **Lens lanes draw on a FIXED 0..1 scale** (motion tracks auto-scale), so the shape of a pull is comparable between takes — and because that scale is fixed and load-bearing, both ends are labelled.
- **3D export carries the lens and omits it honestly.** USD gets animated `focusDistance` (converted by `metersPerUnit`), `focalLength`, `fStop`. An **unmapped** axis is not exported at all — a travel fraction is not a focal length, and writing `0.62` into `focalLength` produces a file that looks valid and is nonsense — so the document carries an explicit `NOT EXPORTED: …` note instead. CSV, the format people open to check things, carries **both** columns.
- **The headless render earned its keep again** (fourth slice running). Code review passed; the picture did not. (1) The live value readout was pinned to each track's **top-right corner**, where it reads as a *scale label* rather than a scrub readout and collides with any key on the last frame — moved onto the playhead, on the line it describes, flipping side near the edge. (2) The fixed 0..1 scale had **no end labels at all**, so a focus lane could be read upside down — the one lane where that matters most. Both fixed before shipping.
- **Disclosure over implication:** nothing drives a lens motor yet, so the timeline band reads `(authoring + export only — no lens device yet)` and Upload appends `focus · iris NOT sent: no lens device`. An operator who assumed otherwise finds out in the rushes.
- **Stage height budget is now spent** as well as the rail's: six tracks fit 1440×880, verified by render. A seventh lane needs scrolling tracks — a real design change, not a tweak.
- 214 tests.

## 2026-08-18 (v0.11 — the lens actually moves · ADR-0018)

Owner supplied the hardware direction at the end of the last slice — Arduino-class board plus stepper driver boards — so ADR-0017 §4 stopped being a specification and became a build.

- **One board, one `GO`.** Lens axes ride the trigger board on **protocol v2**, not a second device. A second board would mean a second port to forget to plug in and, worse, a second clock — cues and focus started by two different `GO`s drift apart, which is the whole thing Tier 2 exists to prevent.
- **A v1 cue board still connects.** ADR-0004 says never guess at a command set you do not know; v1 is one we *do* know. Refusing a working cue board because the app grew a feature it lacks would be the rule applied past the point where it protects anyone. `SUPPORTED_TRIGGER_PROTOCOLS = [1, 2]`; anything else is still refused outright, and the UI says "no lens axes — cues only" rather than "not connected", so nobody goes looking for a cable.
- **The host sends samples, not keys — and decimates them under a stated bound.** Putting the spline in an `.ino` would create a second motion solver and the curve the operator draws would stop being the curve the rig pulls. But per-frame is 1731 points for a three-lane 24-second move: 34 kB down a serial line while a performer stands still. Douglas–Peucker with a **vertical** error metric fixes it — vertical, not perpendicular, because perpendicular distance mixes milliseconds and travel units into one number whose answer changes if you express the move in seconds. Vertical distance bounds exactly the thing worth bounding: *how far the device's linear interpolation can be from the spline, at any instant*, in the same units the wire uses — so the bound can be stated in **motor steps**. At half a step on a 4000-step barrel: 132 points, 2.4 kB, 0.21 s. Nothing observable given up, because the residual is finer than the motor can resolve. Consequence recorded in the firmware: **it may only interpolate linearly.** "Improving" it with smoothing would silently invalidate the number.
- **The peak rate for the feasibility pre-flight is measured on the DENSE curve.** A decimated chord's slope is a weighted average of the slopes it replaces, so it can never exceed the dense maximum — measuring dense is the conservative choice and means decimation can never quietly hide a snap focus from the check that would have warned about it.
- **Uploads are chunked and cross-checked.** An ATmega's UART buffer is 64 bytes and in principle the firmware keeps up — but "in principle the firmware is never busy" is exactly the assumption that produces a silently truncated focus pull. `LSYNC` every 32 points, plus `ARM` reporting its own lens count for the host to compare against what it sent. Over-capacity behaves identically by construction: the board drops what it has no room for, the count comes back short, the pass is refused. There is no path where a truncated pull runs.
- **Calibration is mandatory and only the board may claim it.** A stepper is open loop; `LCAL` against both stops is the only thing that makes a position mean anything. The host remembers the travel figure between sessions **as a pre-flight hint only** — because only the board knows whether it has seen a stop since it powered up. An axis with a curve and no homing makes `GO` answer `LERR` instead of `STARTED`, and the app turns that into a sentence rather than a timeout the operator has to guess at.
- **`ABORT` stops and HOLDS.** Never homes, never releases, drivers stay enabled. A focus ring free-wheeling under a heavy lens on a tilted head is how you lose a lens. The host also clears its uploaded-point count on abort, so the next `ARM` cannot "pass" by comparing against a run that was abandoned.
- **I got `invert` wrong in v0.10, and fixed it rather than documenting around it.** ADR-0017 put "motor runs backwards" on the lens axis, in the move file. Which way a motor turns is a fact about a rig on a day; a file carrying it reverses somebody else's focus pull the moment they open it — precisely the failure ADR-0016 moved cue bindings into preferences to avoid. **Schema v4** strips it and writes the fact into `notes` (the v1→v2 timebase idiom), the setting moves to prefs, and the firmware reconciles handedness at the DIR pin where it physically lives. Display, 3D export and the wire encoder all got *simpler* — which is usually how you know. Two schema versions in two days is the price of having got it wrong; a file that behaves differently on different rigs would have been the price of leaving it.
- **The reference firmware was the only part of the repo nothing checked. Now it has two checks, both in CI, and they found two real bugs on first run.**
  1. **A host exercise** — `Arduino.h` shimmed on the desktop with a fake clock, a pin array, and a *simulated barrel with hard stops* that moves on STEP rising edges in whatever direction DIR says (so it exercises the handedness handling rather than assuming it). Caught `seekStop` backing off a stop in the **wrong direction**: standing on the low stop and about to travel up, it stepped *down*, went nowhere, and returned zero travel. Every calibration would have looked like a dead motor.
  2. **A protocol parity check** — one script file fed to both the TypeScript `SimulatedTriggerDevice` and the C++ firmware, replies diffed with clocks normalised. This is the one that matters: the host is written against the simulator, so **a simulator more permissive than the board means every test passes and the rig fails.** Caught the simulator accepting `LAXIS 9` on a three-axis board. The script file is now the contract — add a case whenever the protocol grows.
- **One pre-flight gate for the whole pass.** Unroutable cues and infeasible lens speeds are reported together, because two gates are two chances to skip one and both failures cost the same thing.
- **The render pass earned its keep again** (fifth slice running). The ⌾ Lens… modal had the jog slider down in the motor block, which broke the marking loop — the workflow is *drive the barrel to a witness mark, read what it says, type it in*, so the jog belongs beside the "At" field it fills. It also wrapped the Calibrate button onto its own line where it read as unrelated to the device chip. Both regrouped; the marks list is now capped and scrolls, because a real lens map runs to a dozen marks and the sheet must not outgrow the window.
- 248 core tests · 19 firmware checks · protocol parity across 21 commands.
- **Process failure, mine.** I handed over a command block containing `npm test --prefix packages/nmx-protocol   # 248`. **zsh does not enable interactive comments by default**, so `#` and `248` went to vitest as test-name filters and it exited with "No test files found" — the suite never ran on the owner's machine, and v0.11 was committed and pushed without it. CI covers it, but the instruction was wrong and it read like a broken repo. Fixed at the root: **`./scripts/check.sh`** now runs build, typecheck, core tests, CLI smoke, firmware exercise and protocol parity in CI's own order, so the handed-over command is one line with nothing to misparse. **Rule: never put a `#` comment in a command line handed to someone else's shell.**

## 2026-08-19 (v0.12 — the lens library · ADR-0019)

ADR-0017 put lens marks in the move file. Right for one move, wrong for a shoot: a 35 mm prime has the same marks on Tuesday it had on Monday, and marking a barrel is careful physical work — drive to a distance, check it against a tape, write it down, repeat. Ask for that every setup and it stops happening, and the lane quietly degrades to percent, which repeats perfectly and tells the operator nothing. Preston stores 150 lenses for exactly this reason; the number is what a rental house's worth of glass looks like.

- **Merge on `id`, never on name.** Two people can call a lens "35mm" and mean different glass, and the same lens renamed is still the same lens. Names are for humans, ids are for merging. Ids are readable and derived (`focus-zeiss-cp-3-35mm-k3f9`) rather than opaque UUIDs so a library file stays human-editable — and the entropy is the caller's, keeping the core pure and testable.
- **Import merges and reports; it never replaces.** Someone hands you their library and losing your own marks in exchange is not an import, it is an accident.
- **One malformed entry does not sink the file.** 150 lenses with one bad one: refusing the 149 good ones helps nobody. Survivors go in, casualties are named. Deliberately the **opposite** of how a move file is treated — a move is one indivisible thing whose partial load would be a wrong move; a library is a collection whose partial load is a smaller collection. Worth stating out loud because "be strict about input" is otherwise a reflex.
- **Forgetting a lens does not unmark a move that is using it.** A delete that silently strips marks from an already-marked move is the worst kind of destructive: invisible until the pull comes out wrong. The lane keeps its marks; only the shortcut is gone, and the status line says so.
- **Applying a lens takes an undo snapshot.** It edits the move, so ⌘Z has to reach it.
- **Entry validation delegates to the map validator** rather than growing a second, subtly different set of rules. An entry that would be rejected as a map cannot be used, and finding that out at apply time is finding out too late.
- **The button reads Keep or Update depending on whether the library already has this lens.** "I re-marked this lens" and "I have a second lens with a similar name" are different intentions and the UI should not make you guess which one it heard.
- Render pass caught one thing: the library delete button was a bare `✕` sitting beside a dropdown, where it reads as "clear the selection" rather than "delete this lens permanently". Now labelled **Forget**, which also matches Keep/Update as a verb.
- 264 core tests · 19 firmware checks · protocol parity across 21 commands, all via `./scripts/check.sh`.

## 2026-08-19 (v0.13 — commissioning · ADR-0020)

No steer from the owner this round, so I picked the thing ADR-0015 had been waiting on since v0.7: *"steps→mm/deg needs a calibration MEASURED on the rig; without it an export is a shape, not a camera move."* Five versions of saying that, a procedure in a doc, three number fields in the export dialog, and nothing in between that helped anybody.

- **The measurement is physical and cannot be automated. Everything around it can be.** Reading the step counts, the arithmetic, the error estimate, noticing the answer is a power of two out, remembering the result. Leaving all of that on a clipboard is how a rig ends up with a calibration nobody can defend.
- **Spans, not absolute positions.** An observation is `{steps moved, what the tape said}`, and each contributes its own ratio. A least-squares line through absolute positions is more statistically conventional and has an **intercept** — and the intercept quietly absorbs backlash and measurement offset. A fit that absorbs your errors has stopped telling you about them. The spread between independent spans IS the error bar.
- **Spread is peak-to-peak, not deviation-from-the-mean.** Caught by a failing test I had written with the wrong expectation, and it turned out the metric was the thing that was wrong: with two measurements, deviation-from-the-mean is exactly half the disagreement the operator can see between their own two numbers. A warning that says "these disagree by 5%" while printing 2.5% teaches people to distrust it.
- **With two disagreeing measurements the app refuses to name a culprit.** Both sit the same distance from their own mean; nothing in the arithmetic can say which is wrong, and naming one would be believed. `worst` is null below three spans and the warning asks for a third. This came out of the same failing test — my expectation named the "suspect" observation, and there was no basis for it.
- **Diagnostics compare against the STORED value, not a textbook one.** "You measured 320 and the file says 160" is actionable; "that is unusual for a slider" is not. ADR-0015's two traps get named explicitly: ~×100 is a unit slip, a clean power of two is the driver's microstep jumper. Both produce a number that looks entirely reasonable alone and is an order of magnitude out in the export.
- **The laser method for rotation**, because a protractor taped under a tripod is not a measuring instrument. Laser square at a wall, mark, rotate, mark, measure between: `atan(offset/distance)`. Warns above 25° where "started square" stops being free and below 5° where the angle is too small to read.
- **Repeatability reports bias and scatter separately.** A consistent offset every pass is backlash or belt take-up and is largely correctable; scatter either side of zero is lost steps and is not. One number would hide the distinction exactly when it matters.
- **The panel carries its own jog buttons and its own live position readout.** The procedure is jog-to-a-mark, walk away with a tape, come back and type — a dialog covering the rail's jog controls would make the thing it exists for impossible. The render pass caught the second half of that: I had jog buttons but no step readout, so you would have been jogging blind inside the panel that exists to read step counts.
- **The render also caught dead code I had written myself.** `degreesFromLaser` and `laserAngleWarning` were in the core with tests and no way to reach them from the app — the same failure as a test that asserts nothing, one level up: capability the project claims and does not offer. Wired into the panel for pan and tilt.
- **A real latent bug, found by asking what happens next.** `-apply` writes main's calibration, but the export dialog keeps its own `exPrefs` copy and writes it back wholesale on any field change. Without merging the applied values into that copy, the next keystroke in the export dialog would silently overwrite the numbers just measured — invisible until an export came out at the old scale.
- 290 core tests · 19 firmware checks · protocol parity, all via `./scripts/check.sh`.

## 2026-08-19 (v0.14 — physical controls · ADR-0021)

Picked the backlog item that had been sitting since v0.6 labelled "gamepad button bindings (e-stop on a button)". That label undersold it: **until this slice the only e-stop was a mouse target**, and when a camera is heading somewhere it should not be, the operator is looking at the rig with a controller in their hands, not at a cursor.

- **The rule, and it is deliberately asymmetric: stopping is instant and always available; starting requires deliberation.** STOP fires the moment the button goes down — no hold, no confirmation, no check on what the app is doing. An e-stop that asks a question is not an e-stop. Anything that can put the rig in motion is a **600 ms hold**.
- **Hold, not double-press.** A bouncing or sticky button can produce a double-press on its own; nothing produces 600 ms of continuous contact. A hold can also show progress while it happens, so the control teaches itself instead of surprising people.
- **The latch fires once per press, not repeatedly while held.** A held button is one instruction; a Run pass that retriggered every tick would restart the move the instant it finished.
- **Two loops, and the split is the point.** The jog loop only runs when gamepad jog is toggled on. Hanging the e-stop off that would have made it work *only while jogging* — and the moment you most want a physical stop is during a **programmed pass**, which is exactly when jog is off. The button loop runs at 40 ms whenever a controller is present, whatever dialog is open, whatever has focus.
- **Nothing is bound by default.** A guessed e-stop button is worse than none, because the operator would believe in it. Button indices are not standardised across devices, so any default is a guess. The absence is shown in red instead, and two actions on one button is reported as the ambiguity it is.
- **The policy is bridged from the core, not copied** — same reasoning as the timecode bridge. "Starting requires deliberation" having two homes is how it quietly stops being true in one of them. A test walks the action list and fails if the stop action ever grows a hold or a motion action ever loses one.
- **A live bug, found by reading the loop I was about to extend.** The jog poll did `if (!pad || !connected) return;` — so a controller whose USB dropped mid-jog left **the last commanded jog speed still running**. The firmware's joystick watchdog would have caught it eventually, which is what it is for, but "eventually, by a timeout we have never measured" is not how a moving camera gets stopped, and nothing told the operator. Now it zeroes every axis immediately, says so, and logs it.
- **The render pass earned it again, twice.** Adding a Buttons section pushed the gamepad dialog past its sheet and **silently clipped the live-response canvas** — fixed generally (no `.sheet` may clip its own content) rather than locally. And the hold-progress bar was present, correctly styled, correctly coloured, and **zero pixels tall**: a flex child shrinking to nothing in an over-full column. That one was only found by *measuring* the rendered geometry rather than looking at the picture — worth remembering that looking is not always enough.
- 307 core tests · 19 firmware checks · protocol parity.

## 2026-08-19 (v0.15 — the connection doctor · ADR-0022)

Owner said hardware lands in two days. That changes what is worth building: the likeliest way a first bring-up session gets eaten is not a bug in the editor, it is ninety minutes on a handshake that times out.

- **One symptom, six causes.** Charge-only cable, unpowered NMX, BLE mode instead of USB, wrong port picked from a list that is mostly Bluetooth, non-default device address, wrong baud rate. All of them present as the same timeout, so they get told apart by swapping things one at a time. Every piece of evidence needed to separate them was already observable — the app just never looked.
- **Count the bytes. Silence and noise are different failures.** Zero bytes means nothing is talking to us. Bytes that never form a valid frame means something *is* talking and we cannot hear it — which is a baud mismatch, or a different device on that path. A timeout throws that distinction away; the probe taps the port's raw data alongside the client so it survives. This is the single most useful thing in the slice.
- **Ask every plausible address, and then say you asked.** A non-default address is a legitimate configuration — it is how two controllers share a bus — and it presents as a completely dead link. The probe asks 3, 2, 4, 5, 6, 7, 8 and stops at the first answer. When silence comes back, the report states that addresses have been ruled out, so nobody spends more of the afternoon on one.
- **The classification is a pure function.** `explainProbe(evidence)` → verdict, headline, ordered steps. No port, no timers, no IO, so the *reasoning* is what is under test rather than the plumbing, and it can be reviewed by reading it.
- **Rank the port list; never hide anything.** Bluetooth and debug entries are marked, not removed. Hiding a port the operator can see in the system would look like a missing device — a worse problem than a cluttered list.
- **The Diagnose button appears at the moment of failure** and disappears on success. Offered before there is a problem it is clutter nobody reads when it matters.
- **Failing to OPEN the port is its own diagnosis** and a much more specific one than any probe could infer: something else has the port — a serial monitor, the Arduino IDE, a second copy of the app.
- **`SimulatedNmx` gained `off()`.** The probe taps a port temporarily and must detach; a real `SerialPort` can, and a simulator that cannot is a simulator that quietly leaks. Same rule the firmware parity check enforces: **the simulator must be at least as capable and at least as strict as the thing it stands in for.** There is now a test that fails if the probe leaves a listener behind.
- Deliberately NOT done: auto-connecting to whatever address answers. Convenient, and it hides a rig configuration the operator should know about — two controllers silently adopting addresses is a much worse afternoon than one clear message.
- 324 core tests · 19 firmware checks · protocol parity.
